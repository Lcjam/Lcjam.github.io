인덱스를 걸면 조회가 빨라진다는 건 잘 알고 있죠. 근데 왜 하필 B+Tree인지, PK를 UUID로 잡으면 왜 INSERT가 느려진다는 건지 물어보면 말이 안 나오기 마련입니다.

그래서 이번에는 MySQL InnoDB를 기준으로 인덱스가 어떤 구조로 디스크 I/O를 줄이는지부터 InnoDB의 클러스터드 인덱스, 그리고 그게 JPA 엔티티 설계 어디에서 드러나는지까지 한번 알아보도록 하겠습니다.

## 1. 인덱스가 하는 일

인덱스가 없으면 DB는 조건에 맞는 행을 찾으려고 테이블을 처음부터 끝까지 읽습니다. 이게 Full Table Scan이고 비용은 O(N). 인덱스는 특정 컬럼 값으로 정렬해 둔 별도의 자료구조라서 원하는 레코드 위치를 O(log N)에 찾아갈 수 있습니다.

`WHERE` 조건 검색뿐 아니라 `ORDER BY` 정렬, `GROUP BY` 그룹핑, `JOIN`에서도 디스크 I/O 횟수가 줄어서 `SELECT`가 빨라지죠.

대신 공짜는 아닙니다.

- 인덱스 페이지를 따로 저장할 공간이 들고, 인덱스 개수가 늘고 컬럼이 길수록 커집니다.
- `INSERT`, `UPDATE`, `DELETE` 때마다 원본 테이블뿐 아니라 인덱스 트리의 정렬 상태도 맞춰야 합니다. 페이지가 꽉 차면 페이지 분할(Page Split)까지 일어나서 쓰기가 느려지죠.

## 2. 왜 해시 테이블도 B-Tree도 아니고 B+Tree인가

| 자료구조 | 탐색 | 구조 | DB 인덱스로 쓸 때 |
|---|---|---|---|
| 해시 테이블 | O(1) (동등 비교) | 해시 함수로 키를 매핑해 저장 | 정렬돼 있지 않아서 `>`, `<`, `BETWEEN`, `LIKE 'abc%'` 같은 범위 검색을 못 한다 |
| B-Tree | O(log N) | 루트, 브랜치, 리프 모든 노드에 키와 데이터(또는 주소)를 같이 저장 | 브랜치에도 데이터가 들어가서 노드 하나에 담기는 키가 적다. 트리가 높아지고 범위 검색 때 트리를 오르내려야 한다 |
| B+Tree | O(log N) | 브랜치는 길 찾기용 키만 저장하고 데이터(또는 주소)는 리프에만 둔다. 리프끼리는 연결 리스트로 이어진다 | 노드 하나에 키를 더 많이 담아 트리가 낮다. 범위 검색은 리프를 옆으로 따라가면 된다 |

여기서 노드 하나는 디스크 페이지 하나입니다. InnoDB는 기본 16KB 페이지 단위로 읽고요. 브랜치 노드에 데이터 없이 키와 자식 포인터만 넣으면 한 페이지에서 갈라지는 가지 수(fan-out)가 커지고, 그만큼 트리가 낮아져서 루트에서 리프까지 읽어야 할 페이지 수가 줄어듭니다.

```text
          [ 20 | 50 ]                     브랜치: 길 찾기용 키와 자식 포인터만
         /     |     \
        v      v      v
[10|15|20] <-> [25|35|50] <-> [60|75|90]  리프: 실제 데이터(또는 PK) + 양방향 연결
```

교과서 그림에는 리프를 한 방향으로만 잇는 경우가 많은데 InnoDB는 같은 레벨의 페이지끼리 앞뒤로 연결해 둡니다. 그래서 역순 스캔도 리프를 따라가며 처리할 수 있어요.

## 3. 클러스터드 인덱스와 세컨더리 인덱스

| 비교 | 클러스터드 인덱스 | 세컨더리(논클러스터드) 인덱스 |
|---|---|---|
| 개수 | 테이블당 1개 (보통 PK) | 여러 개 (`UNIQUE`, 일반 인덱스) |
| 정렬 | 인덱스 키 순서로 실제 레코드가 저장된다 | 실제 데이터는 그대로 두고 인덱스 페이지만 따로 정렬한다 |
| 리프 노드 | 테이블 레코드 전체 | 인덱스 컬럼 값 + PK 값 |
| 조회 | 리프에 닿으면 모든 컬럼을 바로 읽는다 | 리프에서 PK를 얻고 클러스터드 인덱스를 한 번 더 탄다 (랜덤 I/O 발생) |

InnoDB에서 PK가 없으면 `NOT NULL`인 첫 `UNIQUE` 인덱스를, 그것도 없으면 숨겨진 행 ID로 클러스터드 인덱스를 만듭니다. 그리고 "키 순서로 저장된다"는 건 레코드가 PK 순서로 리프 페이지에 모여 있고 페이지끼리 그 순서로 이어져 있다는 뜻이에요. 페이지가 디스크 위에 연속으로 깔려 있다는 보장까지는 아닙니다.

## 4. JPA 엔티티 설계에서 드러나는 지점

### `@Id`가 곧 클러스터드 인덱스다

MySQL(InnoDB)에서 JPA 엔티티의 `@Id` 필드는 테이블 PK가 되고, PK가 클러스터드 인덱스가 됩니다.

`@Id`를 무작위 UUID(v4)로 잡으면 새 엔티티를 `save()`할 때마다 정렬된 데이터 페이지의 중간 아무 데나 끼어들어야 합니다. 페이지 분할과 단편화가 잦아지고 쓰기 성능이 크게 떨어지죠.

그래서 순차 증가하는 `AUTO_INCREMENT`(`GenerationType.IDENTITY`)를 쓰거나, UUID가 꼭 필요하면 시간순으로 정렬되는 UUID v7이나 TSID를 쓰는 편이 낫습니다.

### 세컨더리 인덱스는 PK를 들고 있다

InnoDB 세컨더리 인덱스의 리프에는 레코드의 물리 주소(Row ID)가 아니라 PK 값이 들어 있습니다. 페이지 분할로 레코드 위치가 바뀌어도 세컨더리 인덱스는 손대지 않게 하려는 설계죠.

대신 PK가 길면 모든 세컨더리 인덱스가 같이 커집니다.

### 커버링 인덱스

쿼리의 `SELECT`, `WHERE`, `ORDER BY`에 쓰인 컬럼이 전부 한 세컨더리 인덱스 안에 있으면 클러스터드 인덱스로 다시 찾아가는 과정(테이블 룩업) 없이 인덱스 리프만 읽고 끝납니다. 이게 커버링 인덱스예요. 세컨더리 인덱스에는 PK가 이미 들어 있으니 PK 컬럼은 따로 넣지 않아도 커버되고요.

데이터가 많은 테이블의 페이징 쿼리에서 효과가 큽니다. `EXPLAIN` 결과의 `Extra`에 `Using index`가 찍히면 커버링 인덱스로 처리된 겁니다.

```java
// JPA 엔티티에서 복합 인덱스 선언 예시
@Entity
@Table(name = "orders", indexes = {
    // 카디널리티가 높고 등호(=) 조건으로 자주 쓰이는 member_id를 선두 컬럼으로 배치
    @Index(name = "idx_orders_member_created", columnList = "member_id, created_at DESC")
})
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "member_id", nullable = false)
    private Long memberId;

    @Column(name = "created_at", nullable = false)
    private LocalDateTime createdAt;
}
```

### 복합 인덱스는 컬럼 순서가 중요하다

복합 인덱스 `(A, B)`는 `A`로 먼저 정렬하고, `A` 값이 같은 것끼리만 `B`로 정렬합니다. 그래서 `WHERE B = ?`처럼 선두 컬럼 `A` 없이 `B`만 조건으로 주면 인덱스로 범위를 좁히지 못하죠. MySQL 8.0.13부터는 옵티마이저가 Skip Scan으로 이런 경우에도 인덱스를 쓰기도 하지만 조건이 꽤 까다로워서 기본 동작으로 기대하긴 어렵습니다.

그래서 조건절에 자주 나오고 카디널리티가 높은 컬럼을 앞에 둡니다. 다만 `>`나 `BETWEEN` 같은 범위 조건이 걸리는 컬럼은 뒤로 미는 게 보통이에요. 범위 조건 뒤에 오는 컬럼은 탐색 범위를 좁히는 데 쓰이지 못하기 때문입니다. 위 예시에서 등호로 찾는 `member_id`가 앞에, 정렬과 범위에 쓰이는 `created_at`이 뒤에 있는 것도 그래서고요.

## 5. 면접에서 자주 나오는 질문

### 왜 해시 테이블이나 B-Tree가 아니고 B+Tree인가

답의 뼈대는 범위 검색과 디스크 I/O 두 가지입니다.

해시 테이블은 `=` 비교는 O(1)로 빠르지만 데이터가 정렬돼 있지 않아서 `<`, `>`, `BETWEEN`, `ORDER BY` 같은 범위 연산을 처리하지 못합니다.

B-Tree 대신 B+Tree를 쓰는 이유는 둘입니다. 첫째, 브랜치 노드에 데이터 없이 키와 포인터만 두니 디스크 블록 하나에 키가 훨씬 많이 들어가고 트리 높이와 디스크 I/O가 줄어듭니다. 둘째, 데이터가 있는 리프 노드가 연결 리스트로 이어져 있어서 범위 검색 때 루트로 다시 올라가지 않고 리프만 순서대로 읽으면 되죠.

### 클러스터드 인덱스와 세컨더리 인덱스는 뭐가 다른가

가장 큰 차이는 실제 레코드가 인덱스 순서로 정렬돼 저장되느냐, 그리고 리프 노드에 뭐가 들어 있느냐입니다.

클러스터드 인덱스는 테이블당 하나뿐이고 인덱스 키 순서대로 실제 데이터가 저장되며 리프 노드 자체가 데이터 행입니다.

세컨더리 인덱스는 여러 개 만들 수 있고 실제 데이터는 건드리지 않은 채 인덱스 페이지를 따로 구성합니다. InnoDB에서는 리프에 인덱스 컬럼 값과 PK 값이 들어 있어서, 세컨더리 인덱스로 조회하면 PK를 찾은 뒤 클러스터드 인덱스를 한 번 더 탐색하죠.

### 꼬리 질문

**인덱스가 있는데도 Full Table Scan이 나는 경우는?**

1. 인덱스 컬럼을 가공했을 때. `WHERE SUBSTRING(name, 1, 1) = '김'`, `WHERE YEAR(created_at) = 2026` 같은 식입니다.
2. `WHERE name LIKE '%단어%'`처럼 `%`로 시작해서 시작 값을 알 수 없을 때.
3. 복합 인덱스의 선두 컬럼이 조건절에 없을 때.
4. 옵티마이저가 풀 스캔이 더 싸다고 판단할 때. 읽을 행이 전체의 20~25%를 넘어가면 인덱스를 거쳐 랜덤 I/O로 읽는 것보다 순차 I/O로 테이블을 통째로 읽는 쪽을 고를 수 있습니다. 이 비율은 경험칙이고 고정된 값은 아니에요.

**카디널리티는 무엇이고 인덱스 설계 때 어떻게 고려하나?**

카디널리티는 컬럼 값이 얼마나 다양한지를 뜻합니다. 중복도의 반대 개념이죠. 성별 컬럼은 카디널리티가 낮고 이메일이나 주문번호는 높습니다. 카디널리티가 낮은 컬럼에 인덱스를 걸면 인덱스를 타도 결국 행 대부분을 다시 읽어야 해서 거르는 효과가 거의 없습니다. 그래서 인덱스는 카디널리티가 높은 컬럼에 겁니다.

**`DELETE`나 `UPDATE`가 잦으면 인덱스에는 무슨 일이 생기나?**

`DELETE`하면 InnoDB는 인덱스 키를 바로 물리적으로 지우지 않고 삭제 표시(delete mark)만 해 둡니다. 실제 정리는 나중에 purge 작업이 하고요. 그 전까지는 공간이 재활용되지 않아서 인덱스가 부풀어 있을 수 있습니다.

`UPDATE`가 인덱스 컬럼 값을 바꾸면 인덱스 입장에서는 수정이 아니라 기존 키를 지우고 새 위치에 넣는 두 번의 작업입니다. 그래서 인덱스 컬럼을 자주 바꾸는 `UPDATE`는 부하가 크죠.
