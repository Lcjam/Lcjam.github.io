멀티스레드, 동시성, 스레드 풀. Java/Spring으로 백엔드를 하다 보면 매일 듣는 말인데 정작 나는 프로세스와 스레드를 "메모리를 공유하느냐 아니냐" 정도로만 구분하고 있었다. 그 정도로는 Spring MVC가 여러 요청을 어떻게 동시에 처리하는지, 싱글톤 빈에 왜 상태를 두면 안 되는지가 설명되지 않았다.

그래서 메모리 구조와 컨텍스트 스위칭부터 다시 짚고 그게 Spring 애플리케이션 어디에서 드러나는지까지 이어서 정리해 봤다.

## 1. 프로세스

프로세스는 실행 중인 프로그램이다. 빌드한 Java 애플리케이션을 `java -jar app.jar`로 띄우면 운영체제가 `java` 프로세스를 만든다. 그 안에서 JVM이 초기화되고 애플리케이션이 돌기 시작한다.

운영체제는 프로세스마다 독립된 가상 주소 공간을 준다. 그 안의 메모리는 보통 이렇게 나눠서 설명한다.

| 영역 | 역할 |
|---|---|
| Code (Text) | 실행할 프로그램의 명령어 |
| Data | 전역 변수, 정적 변수 |
| Heap | 실행 중 동적으로 할당되는 메모리 |
| Stack | 함수 호출 정보, 지역 변수 |

네이티브 프로그램 기준으로 단순화한 그림이고 실제 배치는 운영체제와 실행 환경마다 다르다. JVM의 런타임 영역과도 일대일로 맞아떨어지지 않는다. 이건 6장에서 따로 본다.

프로세스끼리는 이 주소 공간이 분리돼 있어서 보통은 한 프로세스가 다른 프로세스의 메모리에 직접 접근할 수 없다. 덕분에 한쪽에 문제가 생겨도 다른 쪽 메모리까지 직접 망가지는 일은 피할 수 있다. 다만 격리가 지켜 주는 건 메모리까지다. 공유 자원 문제나 운영체제 전체를 흔드는 장애는 이걸로 막지 못한다.

메모리가 분리돼 있으니 프로세스끼리 데이터를 주고받으려면 별도 통로가 필요하다. 이게 IPC(Inter-Process Communication)이고 파이프(Pipe), 소켓(Socket), 공유 메모리(Shared Memory) 같은 방식이 있다.

## 2. 스레드

스레드는 프로세스 안에서 돌아가는 실행 흐름이다. 프로세스 하나에 스레드가 여러 개 있을 수 있고 각 스레드는 따로 명령어를 실행한다. 프로세스가 주소 공간과 자원을 마련해 두면 그 안에서 실제로 일을 하는 단위가 스레드다.

### 무엇을 공유하고 무엇을 따로 갖나

한 프로세스에 스레드 A와 B가 있다고 해 보자. 같은 프로세스 소속이니 Code, Data, Heap은 같이 쓴다. 대신 실행 흐름은 각자 이어 가야 하므로 Stack과 실행 상태는 따로 갖는다.

![프로세스와 스레드의 메모리 구조 비교](memory-structure.png)

| 구분 | 스레드 A | 스레드 B |
|---|---|---|
| Code | 공유 | 공유 |
| Data | 공유 | 공유 |
| Heap | 공유 | 공유 |
| Stack | 개별 | 개별 |
| PC 및 레지스터 상태 | 개별 | 개별 |

PC(Program Counter)는 다음에 실행할 명령어의 위치다. 스레드마다 어디까지 실행했는지, 지금 어떤 함수를 호출하고 있는지가 다르니 이 상태도 스레드별로 있어야 한다.

메모리를 공유하니 편하기도 하고 위험하기도 하다. 프로세스끼리는 IPC를 거쳐야 하지만 같은 프로세스의 스레드끼리는 공유 데이터로 비교적 쉽게 정보를 주고받는다. 대신 동기화 없이 여러 스레드가 같은 데이터를 동시에 바꾸면 예상 못 한 결과가 나올 수 있다. 이 문제는 뒤에서 싱글톤 빈과 엮어서 다시 본다.

## 3. 컨텍스트 스위칭

여러 스레드가 동시에 도는 것처럼 보이는 이유 중 하나는 운영체제가 CPU 코어의 실행 대상을 빠르게 전환하기 때문이다. 이때 일어나는 게 컨텍스트 스위칭(Context Switching)이다. 지금 실행 중인 작업을 멈추고 다른 작업을 실행하려고 필요한 실행 상태를 저장하고 복원하는 과정이다.

스레드 A에서 B로 넘어간다면 대략 이런 순서다.

1. 스레드 A의 PC, 레지스터 등 실행 상태를 저장한다.
2. 스레드 B의 상태를 복원한다.
3. CPU가 스레드 B를 이어서 실행한다.

상태를 저장하고 복원하는 비용이 들고 CPU 캐시나 TLB 효율도 떨어질 수 있다.

### 프로세스 전환과 스레드 전환은 뭐가 다른가

갈리는 지점은 주소 공간을 바꿔야 하느냐다. 다른 프로세스로 넘어가면 보통 가상 주소 공간도 바꿔야 한다. 그 과정에서 페이지 테이블 전환과 TLB 효율 저하 같은 비용이 붙을 수 있다. 같은 프로세스 안에서 스레드끼리 넘어가면 주소 공간을 그대로 쓰니 이 작업이 필요 없다. 그래서 보통은 같은 프로세스 안의 스레드 전환 쪽이 비용이 적다.

그렇다고 "스레드 전환은 항상 빠르다"고 단정하면 안 된다. 프로세스가 바뀐다고 캐시와 TLB가 매번 통째로 비워지지는 않는다. 요즘 CPU와 운영체제에는 불필요한 TLB 비우기를 줄이는 최적화(x86의 PCID 같은)가 들어가 있다. 스레드 전환 역시 레지스터만 바꾸면 끝나는 가벼운 작업이 아니다. 같은 주소 공간을 쓰는 스레드 전환이 피할 수 있는 건 주소 공간을 바꾸는 추가 비용이다. 실제로 얼마나 차이 나는지는 실행 환경마다 다르다.

## 4. Spring MVC는 여러 요청을 어떻게 처리할까

여기까지 정리하고 나니 궁금해졌다. Spring Boot 애플리케이션에 여러 사용자가 동시에 요청을 보내면 서버 안에서는 무슨 일이 일어날까? 가장 흔한 구성인 Spring MVC와 내장 Tomcat, 플랫폼 스레드 기준으로 보자.

### Tomcat의 스레드 풀

Tomcat은 요청마다 프로세스를 새로 띄우지 않는다. 미리 만들어 두었거나 필요할 때 만든 작업자 스레드(Worker Thread)가 요청을 맡는다. 사용자 A와 B가 동시에 API를 호출하면 이렇게 된다.

- 사용자 A → Worker Thread 1 → Controller → Service
- 사용자 B → Worker Thread 2 → Controller → Service

일을 마친 스레드는 바로 종료되지 않고 풀에 남아 다른 요청에 재사용될 수 있다. 스레드 풀을 쓰는 건 매번 스레드를 만들고 없애는 비용을 아끼고 동시에 도는 스레드 수를 묶어서 서버 자원을 관리하기 위해서다.

요청을 처리하는 스레드의 상한은 Tomcat의 `maxThreads`가 정한다(내부 스레드 풀을 쓰는 일반적인 구성 기준). Spring Boot에서는 `server.tomcat.threads.max`이고 기본값은 200이다. 동기식 요청이 몰려 스레드가 다 차면 새로 들어오는 연결은 대체로 이렇게 밀린다. 기본값은 글을 쓰는 시점의 Spring Boot 문서 기준이다.

1. Tomcat이 이미 받아 둔 연결의 요청은 스레드가 빌 때까지 기다린다. Tomcat이 동시에 붙잡고 있는 연결 수의 상한은 `server.tomcat.max-connections`(기본 8192)다.
2. 이 상한에 이르면 추가 연결은 OS 대기열에 놓인다. 대기열 길이는 `server.tomcat.accept-count`(기본 100)인데 운영체제가 이 값을 그대로 따르지 않을 수도 있다.
3. 대기열마저 넘치면 연결이 거부되거나 타임아웃이 날 수 있다.

스레드를 무작정 늘린다고 성능이 그만큼 오르지도 않는다. 동기식으로 요청을 처리하는 스레드는 외부 API나 DB 응답을 기다리는 동안에도 붙잡혀 있다. 그래서 풀 크기와 요청 하나의 처리 시간이 같이 처리량을 좌우한다.

참고로 Java 21부터는 가상 스레드(Virtual Thread)를 쓸 수 있고 Spring Boot도 3.2부터 `spring.threads.virtual.enabled=true`로 지원한다. 이걸 켜면 `server.tomcat.threads.max`는 효과가 없다. 그러니 모든 Spring MVC 애플리케이션이 위의 작업자 스레드 풀 모델로만 도는 건 아니다.

## 5. 스프링 빈은 왜 무상태(Stateless)로 설계해야 할까

스레드가 메모리를 공유한다는 얘기는 Spring의 싱글톤 빈으로 바로 이어진다. Spring 컨테이너가 관리하는 빈의 기본 스코프는 싱글톤이다. 한 컨테이너 안에서 빈 정의 하나당 객체를 하나만 만들어 공유한다는 뜻이다. `@RestController`를 붙인 컨트롤러도 마찬가지다.

그래서 같은 컨트롤러로 들어온 요청이라면 서로 다른 스레드에서 처리되더라도 같은 인스턴스에 접근할 수 있다.

```java
@RestController
public class VisitController {

    private int count = 0;

    @GetMapping("/visit")
    public int visit() {
        return ++count;
    }
}
```

방문 횟수를 하나씩 올리는 단순한 코드지만 여러 스레드가 동시에 `visit()`을 실행하면 문제가 생길 수 있다. `++count`는 원자적(Atomic) 연산이 아니다. 값을 읽고 1을 더한 뒤 다시 저장하는 세 단계로 이뤄진다. 두 스레드가 같은 값을 읽은 뒤 각자 더해서 저장하면 증가 한 번이 결과에서 사라질 수 있다. 동기화가 없으니 한 스레드가 바꾼 값이 다른 스레드에 제때 보인다는 보장도 없다.

이렇게 여러 실행 흐름이 공유 상태에 접근하는 순서나 타이밍에 따라 결과가 달라지는 문제를 경쟁 상태(Race Condition)라고 한다.

### 그럼 어떻게 짜야 할까

평범한 Controller나 Service라면 요청별 데이터를 인스턴스 필드에 두지 말고 메서드 파라미터와 지역 변수로 처리하는 게 안전하고 단순하다.

```java
@RestController
public class GreetingController {

    @GetMapping("/greet")
    public String greet(@RequestParam String name) {
        String message = "Hello, " + name;
        return message;
    }
}
```

요청이 올 때마다 메서드가 따로 실행되고 지역 변수 `message`도 그때그때 새로 생긴다. 여러 요청이 같은 컨트롤러 인스턴스를 쓰더라도 `message` 변수 자체는 서로 공유하지 않는다.

물론 지역 변수를 쓴다고 동시성 문제가 다 풀리지는 않는다. 지역 변수가 가리키는 객체를 다른 스레드도 참조하고 있다면 그 객체는 여전히 공유된다.

모든 싱글톤 빈이 꼭 무상태여야 하는 것도 아니다. 공유 상태가 필요하면 상태와 연산에 맞춰 `AtomicInteger`, `synchronized`, Lock 같은 동기화 수단을 골라 쓰면 된다. 서버 인스턴스가 여러 대인데 방문 횟수를 일관되게 세야 한다면 DB 같은 외부 저장소로 빼야 할 수도 있다. 그래도 출발점은 불필요한 공유 가변 상태를 만들지 않는 것이다. 그게 동시성 문제를 줄이는 가장 단순한 방법이다.

## 6. JVM 메모리 구조와 연결해 보기

마지막으로 JVM 쪽에서 보면 런타임 데이터 영역도 스레드별 영역과 공유 영역으로 나뉜다.

스레드마다 PC 레지스터와 JVM Stack이 따로 있다. JVM Stack에는 메서드를 호출할 때마다 스택 프레임(Stack Frame)이 쌓이고 프레임에는 지역 변수와 피연산자 스택 등이 들어간다. 반대로 Heap과 Method Area는 모든 JVM 스레드가 공유한다. Method Area에는 런타임 상수 풀, 필드·메서드 정보, 메서드 코드 같은 클래스별 구조가 올라간다. JVM 명세도 이 영역을 프로세스의 text 세그먼트에 빗대 설명한다. 다만 어디까지나 비유라서 1장 표와 일대일로 맞춰 보면 안 된다.

Java 객체는 개념적으로 Heap에 할당되고 여러 스레드가 같은 객체의 참조를 들고 있으면 그 객체에 함께 접근할 수 있다. 거꾸로 말하면 Heap에 있다고 모든 스레드가 자동으로 공유하는 건 아니다. 여러 스레드가 같은 객체를 가리키는 참조를 갖고 있어야 실제로 공유가 일어난다. 그래서 지역 변수에 객체 참조가 담겨 있다면 변수 자체와 그 변수가 가리키는 객체를 나눠서 봐야 한다.

JVM 메모리 구조와 Java Memory Model(JMM)은 다른 개념이지만 공유 객체의 가시성과 동기화까지 파고들려면 같이 봐야 한다.

## 7. 정리

| 구분 | 프로세스 | 스레드 |
|---|---|---|
| 개념 | 실행 중인 프로그램의 인스턴스 | 프로세스 안의 실행 흐름 |
| 주소 공간 | 보통 프로세스마다 독립 | 같은 프로세스 안에서 공유 |
| 데이터 통신 | IPC(파이프, 소켓, 공유 메모리 등) 사용 | 같은 주소 공간의 변수·객체에 직접 접근 |
| 관리 대상 | 주소 공간, 열린 파일 같은 자원 | PC, 레지스터, 스택 같은 실행 문맥 |
| 컨텍스트 스위칭 | 주소 공간 전환 비용이 붙을 수 있음 | 같은 프로세스면 주소 공간 유지 |
| 주의할 점 | IPC 비용, 자원 관리 | 동기화, 경쟁 상태 |

처음엔 프로세스와 스레드를 메모리를 공유하느냐로만 갈랐다. Spring MVC의 요청 처리와 싱글톤 빈까지 이어 보니 이 구분이 왜 중요한지 조금 더 이해가 됐다. 스레드는 같은 프로세스의 주소 공간을 나눠 쓰면서 스택과 실행 상태는 각자 갖는다. Spring MVC에서는 동시에 처리되는 여러 요청이 서로 다른 스레드에서 같은 싱글톤 빈에 접근할 수 있다. 그러니 빈 안에 공유되는 가변 상태가 있다면 동시성부터 따져야 한다.

다음에는 스레드 풀이 안에서 어떻게 돌아가는지, 그리고 `synchronized`, Lock, `volatile`, `AtomicInteger`가 각각 무엇을 막아 주는지 파 볼 생각이다.
